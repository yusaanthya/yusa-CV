今年三月我換了新工作。新公司是新創環境，鼓勵把 agentic workflow 導入日常工作，我也因此從 Copilot / Antigravity 的使用模式，走上打造個人 harness 這條路。

這段過程中我淘汰了 18 份規劃文件，之後才發現，真正該聚焦研究的不是自動化的範圍，而是 human gate 該放在哪裡：
以前寫 code 、改 code 是很貴的事，所以會需要在進 code 前嚴謹把關，並把重點放在逐行 code review 之上。 

但在 AI 時代，只要前期骨架有設計好，後續迭代的速度已經可以加速到幾乎算沒有成本，甚至只要外部真相來源有管理好，可以極高限度開放 agent 自我治理自動搞定一切。

所以目前實際上的痛點已經從改 code 轉移到該怎麼驗證之上了，我們更要花心思考慮的，其實是怎麼做能減輕人類的理解負擔，無論是系統 owner 自己還是整個軟體開發流程中會遇到的合作夥伴。

**也就是工作中的重點其實已經從軟體工程慢慢轉移到了產品工程。**

想想六個月來跌跌撞撞之中也累積了一些心得，又希望在大 AI 時代定期復健，保留自己組織語言獨立書寫的能力，便決定來挑戰每週手寫一篇心得文，記錄自己的心路歷程 XD

目前預計除了這篇序章以外，還會分成六個章節！

## 膨脹

一開始讓 agent 自己無腦堆疊 harness，速度很快。每次遇到問題就直接改規範，感覺做了很多事。但我很快就發現，如果不定期回頭檢視自己堆了哪些規則，架構反而容易腐化。

因為過度規劃，我掉進了一個坑：文件越堆越多、方向一直變，實作卻跟不上。為了實現無人值守，我從最初的專用 agent 計畫，到設計分類器、規範可寫入工作區，再到串接第三方 SNS 窗口。最後才發現，隨著模型迭代和工作模式改變，這些想得很遠的計畫早已過時，有些甚至官方已經推出可以直接使用的功能。

更崩潰的是，邏輯互斥的規則開始互相打架，連我自己要後續調整 harness 都變得困難。

## 轉折

遇到問題就是要解決，但當時這套個人工作流已經導入日常工作，所以我沒有在第一時間就動手改。

直到看到 Claude Code auto mode 已經能穩定用在正式產品上，我才開始縮減並重構，淘汰了 18 份、約 4923 行的規劃文件，12 個根本沒實作的項目、2 個上線當天就 rollback 的項目，以及一度堆到 59 條、清空時還剩 50 條的 allow rules。

但那次砍掉的只有規劃文件和權限設定，寫給 agent 看的規則本身沒有變少，七週後反而又多了一成。所以十一月我又拆了第二次：把 288 條規則逐條盤點，最後只剩 58 條還留在文字裡，另外 58 條改寫成 script，剩下的 169 條直接拿掉，harness 裡的 markdown 也從約 4590 行縮到約 1517 行。

兩次加起來，大約清掉了 8000 行文字。

這段詳細過程，會和膨脹的部分一起在之後的章節分享 XD

其實現在我正在嘗試用 Claude Code on the web 建立夜間實作 pipeline，試用之後發現，更多當初的構想已經不需要自己手搓了。關於這部分，未來有機會也想和大家分享！

## 理論建立

這套工作流建立後的這六個月當中，我經歷了一番掙扎XD
一開始是花了很多精力思考該怎麼限制 AI agent 的權限、哪些行為是可以放行的、哪些不行、怎麼優化 prompt 和 harness rule 來控制 agent 的行為模式......最後的結果就是人類審核這件事情和工作流綁得很死，實作是變快了沒錯，但一直按 approve 的過程中真的審核了什麼又變得沒有把握，人累得要死又要擔心是否被幻覺蒙騙。

過程中我漸漸發現，在現在的模式下，改 code、甚至重構的成本已經變得很低，真正需要多花人力的地方是在需求理解。
於是我調整了做法：前期直接放手讓 critic agents 互審，只先做好高層次的系統架構，並思考幾個重要情境防止資料狀態被汙染，剩下的細節全都先讓 agent 自己來。等到最後他們吵出結論，再到測試環境跑 e2e、留下對應紀錄，只看資料狀態變化有沒有符合我們一開始先列出的情境。

這期間我的作法也經過很多次迭代，一開始也擔心 agent 會亂來，但最後我想通了，既然改 code 已經變得便宜，其實我需要關心的事情只剩三件：
1. 這次版本更新是否包含難以 rollback 的破壞性操作。
2. 開發當下 ticket scope 該怎麼拆，才不會因為後續驗證規模太大而拖累迭代速度
3. 當下這個改動是否高度耦合，未來迭代時有沒有可能因為 QA scope 過大，需要考慮到人類效率無法負擔而動不了

有趣的是從結論來說其實和過去在做軟體工程時關注的重點差異不會太大，到頭來還是在拆分 scope 並評估風險。

只是過去因為改 code 很貴，所以常常是各方同事配合 RD 做事，而現在貴的事情已經變成了理解需求，所以就我自己的工作模式來說，我現在反而更常花心力在思考該怎麼規劃整個 feature 的交付流程，在過程中該怎麼做才能減輕各方的負擔。

要怎麼實作就見仁見智了，目前社群上常見的是將 agent 分為好幾個角色，我自己的想法大方向也差不多，只是簡化了很多，並沒有真的組織各個不同職能的 agents 。

我想這主要是因為目前工作上我還沒有遇到迭代強度高到每天需要發幾百個 PR 的情況，所以現在先這麼做反而簡單。反正以今年的狀況來看， agentic workflow 迭代的速度非常快，以我自己的認知能力來說，維持目前這樣的規模對我的理解負擔是最小的，我想接下來也還是會繼續觀察社群討論再動態調整吧！

## 接下來會寫什麼

後面的六章主要會分為兩半。

前半預計會更詳細的講我怎麼堆疊文件，堆疊到看不懂自己 harness 的程度，後續又是怎麼發現並做拆減：
1. 膨脹：極度依賴文件規劃，最後導致規則和文件堆到我自己都改不動
2. 拆除：最後我其實拆了兩次，會講述兩次各做了什麼事情，以及後來是怎麼發現第一次其實沒有拆乾淨的
3. 防止 over design：主要會講到過度設計這件事，以及思考現在 agent 多做的事情為什麼比以前貴了

後半則是會提到改變之後，該怎麼確保每個 human gate 都能讓人便於理解：

4. critic review：不逐行看 code 以後， agent 的互動流程該怎麼設計、又出過什麼問題
5. 會前盤點：該怎麼在開會前把看 code 就能收斂出工程決議的事情消除掉，只留真正需要讓人類做決定的業務邏輯問題
6. 架構圖：該怎麼讓合作夥伴能夠更清楚看出目前實作的進度、還缺了什麼


## 從「軟體工程」轉移到「產品工程」

看完最近英文圈的一些新聞，更加深刻覺得逐行人工 code review 這件事會消失。

事實上我做自己的 side project 時也已經不會人眼看 PR，而是靠前期建立 AC、中期以 feature test 為基礎的 TDD，最後再由 agent review，並把 issue 依嚴重度分級：P0、P1 才 blocking，P2 以下則整理成 known facts，作為未來迭代和 troubleshooting 的參考。

奇妙的是，整理到最後，我還是認為開發節奏在兩三年內會整個大翻盤，回到我最一開始那個模糊的構想：以 feature 本身作為最終成果，細節實作都交給 agent，人類只負責前期的工作流規劃、高層次的架構設計，以及最後驗收的標準。

只是務實面來說，大部分企業內團隊的迭代速度不一定能那麼快，也不一定真的需要完全複製 big tech 的工作模式與商業規模，最終還是回到：在團隊裡，如何以 feature owner 的身分和不同領域的 stakeholder 對接，討論產品的短中長期規劃。

因此短時間內，我還是需要思考如何讓自己的工作流和 harness 更有彈性，以應對不同團隊的開發流程，這也是我目前還在摸索的方向。
